cadet.roles¶

Generic multi-connection server runtime.

What this is for:

Accepts many concurrent client connections, each with its own reader + delay line, all feeding ONE shared request queue in front of a single model. A scheduler (fifo default, or round_robin across clients) picks the next request; the model processes it and the reply goes back on the originating connection (through that connection’s reverse delay line, if any).

What it contains:

  • Request, _FifoScheduler, _RoundRobinScheduler.

  • ServerRuntime: accept loop + feeder-per-connection + scheduler loop; records per request the queue wait, inference time and queue depth at enqueue.

  • build_server().

How it fits into CADET:

cadet serve <config>; the server node’s scheduler field picks the policy. Per-request metrics are written to outputs/<experiment>/<app>/server_metrics.csv (used by the concurrent-load experiments).

System metrics. When metrics.collectors names them, this runtime also runs the per-node collectors (cadet.metrics.collectors) for its own node, around the serving loop, writing <collector>_<node>.csv into the run directory. If the energy collector is among them, each per-request record additionally carries that inference’s own energy: the collector is asked for the average power over the window the request was being processed in, on the same monotonic clock the record’s inference_s is measured on, so the attribution needs no second alignment step. Default is no collectors, and then nothing here changes.

class cadet.roles.server.PeerModels(config, node_name, seed=None, log=None)¶

Bases: object

The network models for each connection into one node, by its peer.

A node can be the far end of several paths at once - N sensors into one gateway, an ego and a roadside feed into one server - and those paths are not the same link. The server used to resolve one path and hand the same hops to every connection, varying only the RNG stream, so a cell whose uplinks differed could not be expressed: the difference was configured and then ignored.

Call it as (client_id, peer_ip) for a plain accept loop, or pass for_source() to cadet.core.transport.MultiConnectionEndpoint.serve() as its model_for, which is the fan-in form. Each connection gets fresh models with their own RNG stream, seeded from the experiment seed so a run stays reproducible.

Peers are told apart by address, which is what a connection carries. Two client nodes on one host therefore cannot be distinguished, and they share the first path declared into this node; that is logged rather than hidden, because the alternative - the client naming itself in band - is a wire change and this is not the place to make one.

cadet.roles.server.build_server(config_path, overrides, run_index, model_dirs, logger=None, node_name=None, rep=0, bind_host=None)¶

Build a ServerRuntime for one run from a config file.

node_name selects which server node to bind (needed when a config has more than one server); it falls back to the first node with role server.

rep names the repetition, because the per-request metrics and the per-node metrics CSVs are written into that repetition’s run directory and two reps of one config would otherwise write to one file.

bind_host overrides the address this server listens on, leaving the config alone. It exists for a role whose container does not hold the address its peers use: a node on another machine is reached at that machine’s address and its container has to listen on one of its own. It cannot be a config override, because the config is hashed into the run id and the orchestrator and the role would then disagree about which run this is.

Parameters:

  • config_path (str)

  • overrides (List[str])

  • run_index (int)

  • model_dirs (List[str])

  • rep (int)

  • bind_host (str | None)

Generic client runtime (paper Fig. 1(b)).

What this is for:

Drives one client run through the pipeline stages (source, frame processing, transport, action translation, metric collection), delegating the per-stage behaviour to an app plugin’s client hooks.

What it contains:

  • RunContext: the shared handles (config, source, transport, output).

  • ClientRuntime: the staged loop.

  • build_client(): assemble context + app for a config/run from the CLI.

How it fits into CADET:

cadet client <config> –node client [–run N] [–rep R] calls build_client() then ClientRuntime.run(). The app (e.g. examples.braking.flat.app) supplies control/encoding/metrics; the source is cadet.sources.carla.CarlaSource.

System metrics. When metrics.collectors names them, the runtime also runs the per-node collectors (cadet.metrics.collectors) for this client’s node, around the loop, writing <collector>_<node>.csv into the run directory. Default is no collectors, and then nothing here changes.

Load generator role: N synthetic clients at a configured rate -> server(s).

What this is for:

Drives concurrent-load experiments. A load node describes N synthetic clients, a send rate, and an arrival process (constant or Poisson). Each client connects to every server node (fan-out) and sends frames in the reference-app wire format, recording round-trip latency. Combined with the server’s per-request metrics (queue wait vs load), this measures contention.

What it contains:

  • LoadRunner: spawn clients, send at rate, collect latencies.

  • build_load(): construct from a config.

How it fits into CADET:

cadet load <config> --app-module examples.reference.app. Targets all server nodes in the config: clients=10, servers=[s] is 10->1; clients=1, servers=[s1,s2] is 1->2.

class cadet.roles.common.StopSignal¶

Bases: object

A role’s stop signal: first a flag its own loop acts on, then its exit.

The orchestrator stops a role with SIGTERM and escalates to SIGKILL after a grace. Python’s default action for SIGTERM ends the process at once, so a role that is stopped rather than finishing by itself never ran its own shutdown path: a server’s finally did not execute and its per-request metrics were never written. Measured: the braking app wrote server_metrics_*.csv because its app stops the loop itself after the brake, while the reference app, whose server waits for work until it is stopped, produced none at all.

install() makes the handler set a flag through on_stop; the loop notices on its next turn and unwinds normally. Raising from the handler would skip the same shutdown path by another route, which is also why the loop’s wait has to be bounded rather than indefinite.

finish() then hands the process back to the signal, so its exit status is the one a signalled process has. That is not cosmetic: the orchestrator reads a worker’s exit code during the active phase to tell a guard that finished its job (code 0 - the braking server is single-shot by design) from one that died under it (non-zero - node exited unexpectedly). A server that flushed its records and then exited 0 would make an operator’s kill look like a clean finish, which is exactly the failure the lifecycle matrix exists to catch.

Signals can only be installed from the main thread, and a role process is one process per role, so this is used from the role’s own run. Off the main thread (a test driving a runtime in-process) install() is a no-op rather than an error, and finish() then has nothing to do.
