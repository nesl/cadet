cadet.metrics¶

Per-frame metric collection for the braking experiment.

What this is for:

Collects one record per transmitted frame and writes a CSV compatible with the original *_latency_location_log.csv so existing analysis scripts keep working. New columns are appended at the end only.

What it contains:

  • ORIGINAL_COLUMNS / NEW_COLUMNS and the combined field order.

  • MetricsLog: accumulate records, mark brake/stop, write CSV, and compute a summary (brake-engage/stop time+location, frames sent, median brake-reaction latency).

How it fits into CADET:

The braking client app (cadet.apps.braking) owns a MetricsLog, adds a record per frame sent, and finalises it on stop. The runtime never writes results into curated dirs; paths come from the resolved config’s outputs section.

How to configure it:

Construct with the output CSV path and the run_id/rep; those populate the appended columns.

Dict[str, Any]

Per-run record of what a link was configured to do and what it actually did.

What this is for:

The three link backends realise a configuration in different ways, and the gap between “configured 60 ms” and “the application saw X ms” is the thing an experiment needs to be able to inspect. Every run therefore writes both: the link parameters as configured, and the effective per-message latency and unanswered counts as measured. Without this the gap is invisible in outputs and has to be reconstructed by hand from logs.

What it contains:

  • MessageStats: what a client role observed (sent, received, and the per-message latencies in milliseconds).

  • link_summary(): a link’s configuration, flattened for the record.

  • write_link_report(): writes link_report.json into a run’s output directory and returns the structure it wrote.

How it fits into CADET:

ClientRuntime calls write_link_report() after the app finishes, for any app that exposes message_stats(). The file sits beside the per-frame CSV and the run marker.

Latency here is message latency: the time from handing a payload to the transport until its reply is taken off the wire. It is deliberately recorded at reply arrival rather than when the application next looks, because a polling loop would otherwise fold its own tick interval into the number.

A route is recorded the same way, with one addition: a composed path has no observable hop (one connection, one timestamp pair), so the record states each hop’s configured percentiles and the end-to-end composition, and the measured half stays what it was - what the application saw end to end. The composed p50 and p99 are the sums of the hops’, which is the intent rather than a prediction: delays add, but a sum of independent samples has a narrower tail than the sum of their p99s, so the composed p99 is an upper bound. Per-hop measurement is a property of realise: relay, where each hop is a real connection.

How to configure it:

Nothing to configure. The configured half comes from config.links and config.routes; the measured half from the app.

cadet.metrics.link_report.route_summary(config, route)¶

Flatten one configured route into the record, hop by hop.

end_to_end is the composition of the hops that act on each direction: the delay percentiles add, the loss is the chance of surviving every hop, and the bandwidth is the slowest hop’s, because hops in series are a pipeline whose bottleneck sets the rate.
