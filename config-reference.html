Config Reference¶

This reference is generated from cadet/config/schema.py by scripts/gen_config_reference.py. To regenerate it after a schema change, re-run that script and copy the output here.

Each enumerated field lists the values a run may ask for. cadet validate names anything else a config asks for and refuses the run.

Link backend semantics¶

links[*].network.mode selects where a link is emulated, and that changes what the other fields mean. The two families are not interchangeable and neither is made to imitate the other.

delay

netem, netwaggle

layer

message-level: the transport’s delay line holds whole application messages

packet-level: a kernel qdisc holds packets, and TCP reacts

distribution

sampled per message, per the configured distribution

the mean and jitter of a netem delay, applied per packet

direction: forward

delays request messages only; replies are untouched

delays every packet leaving the sender, including the handshake and ACKs

direction: reverse

delays reply messages only

delays every packet leaving the listener

loss

drops application messages; a dropped message is never answered

drops packets; TCP retransmits, so the message still arrives

bandwidth_mbps

serialization delay computed per message

a real rate limit on the queue

needs

nothing

netem: NET_ADMIN. netwaggle: the emulation container

What this means in practice¶

A configured delay is reproduced at the message level, and approximately at the packet level. Measured on a 60 ms forward link with the reference app paced at 20 fps: delay gave p50 60.4 ms, while netem and netwaggle both gave p50 ≈ 149 ms. The extra is not emulator error: an isolated request/response probe over the same qdisc measures 60.1 ms. It is TCP: with small paced messages, Nagle holds a write until the previous one is acknowledged, and the acknowledgement is itself behind the configured delay. Setting transport_tuning.tcp_nodelay: true on the sending node brings the same run to p50 110.2 ms.

Configured loss means different things. delay loses messages, so a 1% loss produced 1.25% unanswered frames. netem and netwaggle lose packets under a reliable transport, so the same 1% produced 0% unanswered and showed up as retransmission latency in p99 instead. If an experiment needs observable message loss, use delay or an unreliable transport.

Choose by question, not by fidelity. Use delay to state a per-message latency distribution and have it honoured. Use netem or netwaggle to ask what a real protocol stack does on a delayed, lossy, rate-limited path. netwaggle additionally gives a real topology, a wireless medium and propagation model, and hosts in separate namespaces.

Every run writes link_report.json next to its metrics, holding the configured parameters beside the measured per-message latency and unanswered counts, so the gap is visible per run rather than assumed.
